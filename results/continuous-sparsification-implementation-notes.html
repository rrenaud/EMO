1What was built

EMO models can be pruned to a small task-specific subset of experts while keeping most of their accuracy. The repo already shipped three selection methods (greedy layerwise, easy_ep, random), each of which scores experts cheaply (≈ one forward pass) and cuts by frequency / importance, emitting a structurally-pruned model plus a pruning_metadata.json. This adds a fourth, loss-aware method: Continuous Sparsification (CS).

Instead of a passive forward pass, CS attaches a learnable logit to every routed expert, gates the expert by a temperature-scaled sigmoid, freezes all model weights, and runs a short calibration loop that trains only those mask logits (plus an L1 sparsity penalty) while annealing the temperature upward. The soft mask hardens toward a boolean decision, which is then baked into a structural prune via the existing in-place prune kernel — producing the exact same artifact the other methods produce, so it drops straight into the existing finetune / eval pipeline with zero inference overhead.

2How it works

The objective

Every standard (routed) expert e gets a learnable logit se. During calibration the expert's contribution is gated by a temperature-scaled sigmoid; the loss adds an L1 penalty on the soft gates:

CS objective ℒ = ℒtask( … · σ(β se) … ) + λ ∑e σ(β se)

As β is annealed upward (1 → 200), σ(β se) hardens toward the step function H(se), so the keep/drop decision becomes “se ≥ 0”.

(a) Mask attachment by per-expert output hooks

The class that actually executes for a checkpoint is the hub copy of modeling_emo.py (loaded via trust_remote_code), not the in-repo source — so the mask must be injected on loaded block instances, never by editing modeling_emo.py. The clean way to do that uses one observation: the block sums each expert's contribution as expert(x) · routing_weight, so scaling expert e's output by σ(β se) is identical to scaling its routing weight — maske·expert(x)·rw ≡ expert(x)·(maske·rw). We therefore attach a register_forward_hook to each standard expert and leave the block's own forward completely untouched (nothing to keep in sync with the hub copy): 

# per MoE layer: a trainable mask logit per standard expert (init s_init=3.0 -> gate ~1),
# plus a mutable python float cs_beta updated each calibration step.
moe.cs_mask_logits = nn.Parameter(torch.full((num_standard,), s_init))
moe.cs_beta = beta_start

def hook(_module, _inputs, output, e=e, blk=moe):       # one hook per standard expert
    return output * torch.sigmoid(blk.cs_beta * blk.cs_mask_logits[e])
moe.experts[e].register_forward_hook(hook)

Shared (trailing) experts are simply left unhooked, so their gate stays fixed at 1 and they are never pruned; teardown before saving is just handle.remove() on each hook. An earlier version instead monkeypatched a re-implemented forward onto each block; the hook version was verified to be numerically identical (output and mask-gradient parity to float32 round-off — see §5) while copying none of the block's forward, so it cannot drift from the hub code.

(b) Freeze + optimizer

for p in model.parameters(): p.requires_grad_(False)
mask_params = [blk.cs_mask_logits for blk in moe_blocks]
for m in mask_params: m.requires_grad_(True)
opt = torch.optim.Adam(mask_params, lr=args.lr)

(c) Calibration loop

A DataLoader is built from load_finetuning_dataset(...) + MaskedLossDataCollator (reused from finetune.py), seeded-subsampled to --num-calibration. Per step:

  1. Forward the model; compute CE manually from logits + shifted labels (ignore_index=-100) — avoids contaminating the loss with the model's router aux loss (which is also disabled via output_router_logits=False).
  2. penalty = λ · ∑layers,e σ(β se) computed directly from the params, so even never-selected experts get pushed off.
  3. loss = ce + penalty; backward; clip_grad_norm_; opt.step().
  4. Update β on every block via an exponential schedule from --beta-start to --beta-end.
  5. Log mean gate, fraction se≥0, ce, penalty.

(d) Selection → keep-set

Final score = se (monotonic in σ). Shared indices are always appended. Three modes:

  • per_layer — top (keep_k − num_shared) standard experts per layer ⇒ uniform keep_k.
  • global — rank all standard experts across MoE layers; keep a global budget of (keep_k − num_shared) × num_moe_layers ⇒ per-layer counts vary.
  • threshold — keep standard experts with se ≥ 0 (emergent count, pure CS); a guard keeps at least the single best expert so a layer is never emptied.

(e) Bake + save

Restore the original forward, drop the training-only mask param, run the before/after hidden-state sanity check, then call prune_moe_layer_inplace(...) per layer. The config update + save_pretrained + pruning_metadata.json block mirrors greedy_prune_layerwise_variable.py, tagged pruning_method="continuous_sparsification" with the CS hyperparameters and keep_k_per_layer / experts_kept_per_layer.

3Implementation decisions & gotchas

  • Hook the experts, don't edit (or reimplement) the model forward. The executed class is the hub copy, so editing the in-repo modeling_emo.py would have no effect — and reimplementing the forward risks drift. Scaling each standard expert's output via a forward hook leaves the block forward verbatim. The always_active_experts masked path raises NotImplementedError at attach time (its semantics conflict with masking) — same stance as easy_ep.
  • The mask multiply naturally stays in float. The expert output (bf16) times the float gate promotes to float32 for the op, so the mask gradient isn't degraded by a bf16 round-trip — and the result is re-cast to the hidden dtype inside the block's existing index_add_.
  • Manual CE, router aux loss off. Passing labels to the model would mix in the load-balancing aux loss; computing CE by hand isolates the task signal that should drive the masks.
  • Penalty over all experts, not just selected ones. Computed straight from the parameters, so experts that never appear in any token's top-k are still pushed toward 0.
  • Shared experts are never masked. Their gate is a fixed 1, matching the repo convention that shared experts occupy the trailing num_shared indices.
  • λ is a sharp knob (and only bites in threshold mode). In per_layer/global the budget is fixed by top-k, so λ barely matters. In threshold it decides the emergent count — see the §5 threshold run, where λ=0.2 collapsed every layer to the guard floor.

4CLI & usage

# Standalone selection (emits a pruned model + pruning_metadata.json)
python -m src.hf_training.continuous_sparsify_prune \
    --model allenai/Emo_1b14b_1T --task arc_challenge --split train \
    --prune-keep-k 32 --num-shared-experts 1 \
    --selection-mode global \
    --num-calibration 256 --num-steps 200 \
    --lr 0.1 --beta-start 1.0 --beta-end 200.0 --s-init 3.0 \
    --batch-size 4 --trust-remote-code \
    --save-path /path/to/selected_model

# Full pipeline (select -> finetune -> eval)
./scripts/selective_hf/hf_finetune_with_selective_continuous.sh \
    --model allenai/Emo_1b14b_1T --task arc_challenge \
    --selective-keep-k 32 --num-shared-experts 1 \
    --num-selective-examples 256 --selection-mode global \
    --base-dir /out --relative-dir arc_challenge_cs --run-name cs_global --num-gpus 1

Existing flags match the sibling scripts (--model --task --split --prune-keep-k --num-shared-experts --save-path --batch-size --num-calibration --num-shots --prune-seed --trust-remote-code). CS-specific: --selection-mode --lambda --lr --num-steps --beta-start --beta-end --s-init --max-seq-length --grad-clip.

8Environment notes

  • HF cache must live on /workspace. Set HF_HOME=/workspace/hf_cache inline for every invocation — non-interactive bash doesn't source .bashrc, so the overlay disk fills otherwise. The selection scripts load with device_map="auto" (weights on GPU), so their saves stream GPU→CPU and stay light.
  • df on /workspace is misleading. It reports the underlying MFS cluster backing store (~378T), not the volume quota. A full volume makes large save_pretrained calls die mid-write with exit 120 and no traceback (it wrote shard 1, then ran out of space on shard 2) — which masquerades as an OOM. Check real usage with du -sh /workspace/*.
  • Eval needs trust_remote_code passed explicitly. For a raw checkpoint path (not in the model library), pass it through launch_eval --model-args '{"trust_remote_code": true}'.

9Matched comparison & next steps

Done: the method is implemented, committed, and verified across all three selection modes; the full pipeline (select → finetune → eval) works on a single H100.

The first genuinely comparable run — CS-global vs easy_ep at identical settings (keep_k=32, 1 shared, 256-example calibration, 3-epoch finetune, same eval):

Method (matched)arc_challenge acc_uncond
easy_ep0.535
CS-global0.334
uniform keep_k=32 (reference) / random0.545 / 0.25
Negative result for CS-global at this config. CS-global (0.334) lands far below easy_ep (0.535), barely above chance. The likely cause is visible in §6: global ranks se across layers and spent its budget gutting the late layers (down to 7–8 of 127 standard experts), which appears to wreck the model. Two plausible culprits — (1) se logits are not calibrated to be comparable across layers, so a global ranking is biased; (2) late layers are simply more sensitive than the allocation assumed. This is exactly why the comparison was run before any sweep.

Next steps suggested by this:

  • Try CS-per_layer in the same matched harness — it keeps the uniform budget easy_ep/uniform use, isolating “loss-aware selection” from “non-uniform allocation.” If per_layer ≈ easy_ep, the §6 allocation (not the CS selection) is what hurts.
  • Constrain global's reallocation (e.g. a per-layer floor, or normalize se within each layer before the global ranking) so it can't gut late layers.
  • Only then a small grid (lr, num-steps, β-end; λ for threshold) and, if a cell beats baseline, scale to more tasks / keep_k values for a Pareto sweep.
